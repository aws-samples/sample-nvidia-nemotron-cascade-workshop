## Nano 这一层有什么价值？

本次 Jev 有 14 张非高风险工单不够确定。Nano 接住了其中 14 张，Sonnet 从两层方案的 31 次降到 17 次。
与 Jev → Sonnet 比，三层成功调用成本估算降低 42.0%；类别及完整标签匹配数相同。
这 14 张中，Nano 错而 Sonnet 对的完整标签案例有 0 张；Nano 对而 Sonnet 错的有 0 张。
与原来的 Nano → Sonnet 比，成本估算增加 36.8%，类别匹配从 126/150 变为 150/150。这不是所有指标都更好的替代方案。

实际回放路径：jev：119；jev→sonnet：17；jev→nano：14。这批工单没有走满 Jev→Nano→Sonnet 的工单；“两层都不确定后进入 Sonnet”的分支另有单元测试覆盖。

## 需要保留的限制

- 三层仍漏掉 5 张需要人工复核的工单：P-0075、P-0099、P-0152、P-0155、P-0192。
- 最后一个模型只找回 9/22 张人工复核需求；保留前面各层信号后为 17/22。调用方应使用 review_required 做人工交接。
- 保留信号后，128 张无需人工的工单中有 0 张被误报；这个小样本不能证明今后不会误报。
- 多条工单来自同一个场景模板，不是 150 个完全独立的现实案例。类别 100% 只描述这批样本。
- 阈值在比较前固定：Jev 最低字段置信度 0.8；Nano 0.7。没有根据这批结果回调阈值。
- Jev 的统计置信度与 Nano 的自报置信度都不是已校准的正确概率。下一步应在新数据上验证，而不是凭本次结果宣称通用优势。
- 本次前 59 条 Jev 成功结果来自未生效限速的两次采集；后 91 条通过每次至少间隔 2.4 秒的限速入口收集。批量 Jev 延迟混合了两种采集方式，且包含排队，不能用于模型速度比较。
- 批量缓存记录 150 个成功结果、其中 4 个结果记录了第二次尝试；另有两次中断采集中的 HTTP 429 失败尝试，未计入缓存 total_attempts。总账单费用不能据此完全重建。
- 150 个成功 Jev 结果报告的 Gateway cost 合计为 0；marketCost 合计约 $0.010859。零 Gateway charge 不意味着市场定价免费。
- 另通过真正的 MCP 客户端运行了 3 张工单，观察到 Jev、Jev→Nano、Jev→Sonnet 三条路径。它们是连接和路由验证，不是新的准确率测试集；原始结果见 three-tier-live-smoke.json。

## 如何复算费用列

每条工单先取 strategies[方案].calls，再累加相应 stages[模型].estimated_market_cost_usd；最后对全部工单求和。运行 `node scripts/summarize-three-tier.mjs` 可从原始 JSON 重建本报告。
